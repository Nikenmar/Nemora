## Non-negotiable compatibility baseline

The port must retain all four identities below:

- Data root: `%APPDATA%\Nora`. Electron obtains this through `app.getPath('userData')`, and every `electron-store` database plus the cover cache is rooted there (`src/main/filesystem.ts:25`, `src/main/filesystem.ts:101-274`). The port plan also records that WebView2 cannot directly read Electron/Chromium `Local Storage/leveldb`, so matching the directory alone is insufficient (`docs/tauri-port/00-PLAN.md:79-105`).
- Installed executable: `%LOCALAPPDATA%\Programs\Nora\Nora.exe`. This was confirmed by read-only inspection of a local 3.4.5 installation on 2026-08-11. **INFERRED:** this is electron-builder's per-user NSIS `localappdata\Programs` default, because the YAML does not spell out an install directory (`electron-builder.yml:72-87`).
- Shortcut: `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Nora.lnk`, targeting the executable above. The configured shortcut and executable names are both `Nora` (`electron-builder.yml:1-3`, `electron-builder.yml:72-87`).
- Explicit AppUserModelID (AUMID): `com.sandakannipunajith.nora`, matching the existing shortcut and `appId` (`electron-builder.yml:1`). Read-only inspection of the installed `.lnk` confirmed this value. The new process must call `SetCurrentProcessExplicitAppUserModelID` before creating any window, and the installer must stamp the identical AUMID on the existing/new shortcut. Microsoft requires the explicit AUMID to be consistent across the process, windows, shortcuts, file associations and jump-list/taskbar integration ([Application User Model IDs](https://learn.microsoft.com/en-us/windows/win32/shell/appids)).

Changing any of these is a migration bug, not a cosmetic difference. In particular, Tauri's stock current-user NSIS directory is `%LOCALAPPDATA%\Nora`, not the existing `%LOCALAPPDATA%\Programs\Nora`; a default configuration would install side-by-side ([Tauri v2 Windows installer documentation](https://v2.tauri.app/distribute/windows-installer/)).

### Required monitor-rectangle clamp

The open bug is a fully black restored window when its rectangle straddles two monitors. Tauri does not repair saved geometry; implement the following in Rust (or one carefully tested TypeScript command) using **physical pixels throughout**:

1. Build the candidate rectangle from the active mode's saved position and size. Enumerate current monitors and their work areas.
2. Select the monitor with the largest intersection area. If all intersections are zero, select the monitor whose work-area rectangle is nearest to the candidate center; fall back to the current primary monitor only if enumeration fails.
3. Cap width/height to the chosen work area while respecting the active mode's minimum/maximum constraints. Clamp `x` to `[work_x, work_x + work_width - width]` and `y` to `[work_y, work_y + work_height - height]`.
4. Apply size before position, suppress move/resize persistence during the operation, wait for the settled native rectangle, then persist that final rectangle only.
5. Re-run on startup after the saved size is known, every mini/main/full transition, `WM_DISPLAYCHANGE`, `WM_DPICHANGED`/Tauri `ScaleFactorChanged`, and monitor connection/removal. Never cache the primary display for the process lifetime.

This preserves a mostly visible window on the monitor where most of it already lies, rather than moving every non-primary window to the primary origin as current code does (`src/main/main.ts:823-835`). Test negative coordinates, monitor-above-primary layouts, different DPI scales, a saved rectangle larger than the work area, unplugging the selected display, and a true 50/50 straddle.

## Part B — updater and release-contract migration

### B1. Current Electron update path

1. Production startup initializes the updater and invokes a check; development builds are skipped and concurrent checks are locked out (`src/main/update.ts:22-46`, `src/main/main.ts:307-308`). `autoDownload` and `autoInstallOnAppQuit` are both disabled, while prereleases are permitted (`src/main/update.ts:30-37`).
2. `electron-updater` reads the GitHub provider configured for `Nikenmar/Nora-CMRFork` (`electron-builder.yml:120-124`). Its feed is `latest.yml`: the checked-in example declares `3.4.5-CMR-Fork`, three installer URLs/hashes/sizes and a default installer (`dist/latest.yml:1-14`). Code comments explicitly depend on `latest.yml` for architecture selection (`src/main/update.ts:13-20`).
3. On `update-available`, the app prompts the user; on acceptance it downloads, then prompts again after download (`src/main/update.ts:48-81`). Progress is forwarded to the renderer (`src/main/update.ts:75-79`).
4. On acceptance, `quitAndInstall(true, true)` requests silent install and forced relaunch (`src/main/update.ts:82-92`). The source documents the resulting NSIS flags `/S`, `--force-run` and `--updated` (`src/main/update.ts:86-91`).
5. The custom NSIS `customInit` checks electron-builder's `${isUpdated}` and calls `SetSilent silent`, preventing an install-over update from exposing the installer UI (`build/installer.nsh:1-8`). The product intentionally disallows directory changes, creates a Start-menu shortcut and installs per user (`electron-builder.yml:72-87`).
6. The strict release payload is therefore three `.exe` installers, their three `.blockmap` files and `latest.yml`; the YAML names x64, arm64 and combined artifacts (`dist/latest.yml:2-14`). The tag/version contract remains strict three-number SemVer plus `-CMR-Fork`, e.g. `v3.4.5-CMR-Fork` (`package.json:3`). A draft release or incomplete asset set is not a usable feed.

`.blockmap` files support electron-updater differential downloads. They are part of the legacy feed contract even though the Tauri feed will not consume them.

### B2. Native Tauri v2 updater contract

Use [`tauri-plugin-updater`](https://v2.tauri.app/plugin/updater/) and the process plugin's `relaunch()` after `downloadAndInstall()`. This is a parallel feed, not an in-place format conversion:

- Tauri consumes `latest.json`, not `latest.yml`. Its version must be valid SemVer and its `platforms` object must include the shipped targets such as `windows-x86_64` and `windows-aarch64`; each target contains a direct installer URL and the **contents** of that artifact's `.sig` file.
- Tauri v2 updater signature verification is mandatory and cannot be disabled. Generate the updater keypair once; commit only the public key (`plugins.updater.pubkey` in `tauri.conf.json`). Keep the private key in the release secret store and provide `TAURI_SIGNING_PRIVATE_KEY` at build time, plus `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` if encrypted. Tauri documentation notes that a normal `.env` file is not loaded for this purpose.
- Enable `bundle.createUpdaterArtifacts`. Windows NSIS builds produce `.exe` plus `.exe.sig` per architecture. Tauri's `v1Compatible` zip is for migration from Tauri v1, not from Electron, and is irrelevant here.
- Tauri downloads full signed installers; there is no Tauri equivalent to electron-updater `.blockmap` differential downloads. Do not publish a fake blockmap for native releases.
- Keep update UI semantics familiar: explicit prompt, visible progress, install, then relaunch. Select/test the Windows `installMode` (passive is the documented default); the bridge installer itself should use explicit `/S /UPDATE /R` behaviour after validation.

The maintainer's manual release flow therefore changes from “upload three Electron installers, three blockmaps and `latest.yml`” to a dual-feed transition and then, after legacy retirement, “upload x64/ARM64 signed Tauri NSIS installers, their `.sig` files and a generated `latest.json`.” Before publishing, validate the JSON against the uploaded URLs, verify each signature with the configured public key, install both architectures on representative Windows 10/11 systems, and only then publish the GitHub release. The private signing key must never be uploaded or placed in the repository; losing it prevents existing Tauri installations from trusting new updates, so maintain an access-controlled backup and rotation/recovery procedure.

### B3. Bridge release — exact 10-step sequence

The installed Electron 3.4.5 application can only consume `latest.yml` and NSIS `.exe` artifacts. It cannot discover `latest.json`, so a first Tauri-only “latest” release would strand it. The safest bridge uses one final Electron build to perform renderer-data export and a custom Tauri NSIS installer to replace the executable **without running the old Electron uninstaller**.

1. **Freeze and record the legacy identity.** Before building anything, assert `%APPDATA%\Nora`, `%LOCALAPPDATA%\Programs\Nora\Nora.exe`, `Nora.lnk`, product/executable `Nora`, and AUMID `com.sandakannipunajith.nora`. Verify the existing pinned shortcut launches into the existing taskbar group; take hashes/inventory of representative real user data. The configured identity comes from `electron-builder.yml:1-3` and shortcut/install policy from `electron-builder.yml:72-87`.
2. **Build and test the first Tauri payload before publishing the bridge.** Give it the next strict version, for example `3.5.0-CMR-Fork`. Use Tauri NSIS `currentUser` with a pinned custom template that sets the legacy `INSTDIR` during `.onInit`, before any directory UI or copy. Set the process AUMID before the first window and set the shortcut AUMID to the same bundle identifier. Verify clean install separately, but do not publish yet.
3. **Build the final Electron bridge at the same release version.** It remains a normal Nora app and therefore arrives through the proven `latest.yml` path. On first run it exports every required Chromium `localStorage` value to the versioned migration JSON already called for by the port plan (`docs/tauri-port/00-PLAN.md:89-105`, `docs/tauri-port/00-PLAN.md:142-149`), flushes the existing JSON stores, records counts/hashes, and writes an atomic `migration-ready` marker only after reading the export back successfully.
4. **Make the bridge hand off to a fixed Tauri asset.** After `migration-ready`, it downloads the architecture-correct Tauri NSIS installer from this exact versioned release asset URL, not GitHub `/latest`; verify a hard-coded SHA-512 and preferably the Tauri signature with the embedded public key. Spawn it as `/S /UPDATE /R`, then close Electron cleanly. On any verification/download error, leave Electron and all data usable and offer retry.
5. **Publish one dual-feed, Published/Latest bridge release.** Upload the full legacy contract—three Electron bridge `.exe` files, all three `.blockmap` files and `latest.yml`—and the native contract—Tauri x64/ARM64 NSIS `.exe` files, each `.sig`, and `latest.json`. Use distinct native asset names. Verify tag/version agreement, every URL, architecture mapping, SHA-512, Tauri signatures and the exact required asset count before making it Published.
6. **Validate 3.4.5 → Electron bridge through the live feed.** From a disposable copy of a real 3.4.5 profile, use the in-app updater. Verify both prompts, download progress, silent NSIS update and relaunch (`src/main/update.ts:48-92`, `build/installer.nsh:1-8`). Before native handoff, verify all JSON and localStorage-backed features, the unchanged install directory, `.lnk` file/target/AUMID, taskbar pin, protocol and file-open behaviour.
7. **Perform install-over, never uninstall-then-install.** The Tauri NSIS preflight must detect the legacy installation and `migration-ready`, wait for `Nora.exe` to exit, retain the same `INSTDIR`, overwrite the payload in place, and leave the existing Start-menu and taskbar `.lnk` files intact. Do not invoke the Electron uninstaller: it can remove/recreate shortcut state and break the pin. Only after payload copy succeeds should it update the uninstaller registry entry, file associations and protocol registration, then relaunch the same path.
8. **Import before normal Tauri initialization.** First native boot explicitly selects `%APPDATA%\Nora`, loads existing JSON files without renaming/deleting them, imports the bridge's localStorage JSON into WebView2 before renderer business logic reads it, validates schema/counts, and atomically writes `migration-complete`. If import fails, preserve all legacy files and export, show a recoverable error and retry; never mark completion optimistically.
9. **Verify data, identity and rollback as one acceptance gate.** Confirm preferences, playlists/library/statistics/auth and other localStorage-dependent state; Discord/tray/titlebar/mini-player; file associations and `nora://`; Start-menu shortcut target/AUMID; and that the pre-existing taskbar pin launches the Tauri executable into the same taskbar group. Confirm the native updater accepts a signed test update. Keep bridge/export and rollback material until this gate passes; cleanup must never touch `%APPDATA%\Nora`.
10. **Keep a legacy path after the bridge stops being GitHub Latest.** Every later release must either continue publishing a valid legacy `latest.yml` that routes 3.4.5 to the frozen bridge, with all referenced bridge artifacts available, or host a separately proven immutable legacy feed. Because the existing GitHub provider normally follows the repository's latest Published release (`electron-builder.yml:120-124`), the conservative policy is to mirror the frozen bridge assets and compatible `latest.yml` onto each current release until telemetry/support policy permits retirement. Integration-test this path; do not assume electron-updater accepts cross-tag or absolute-URL tricks without a live 3.4.5 proof.

**Why the same version for bridge and native payload?** It gives the release one human-facing version and permits the final Electron shell to hand off to a fixed same-tag native asset without asking electron-updater to understand another feed. The bridge must trigger the native installer itself; Electron will not treat another artifact at an equal version as an update. **INFERRED:** using distinct bridge/native versions can also work, but creates more feed-ordering and rollback states without improving identity preservation.

### B4. Users who skip the bridge

A direct stock Tauri install over a machine that still has Electron is unsafe. Its default NSIS location would be `%LOCALAPPDATA%\Nora`, producing two installations; the old taskbar pin would still target `%LOCALAPPDATA%\Programs\Nora\Nora.exe`, while a recreated shortcut or different AUMID could form a second taskbar identity. Even if the new app points at `%APPDATA%\Nora`, WebView2 cannot consume the existing Chromium `Local Storage/leveldb` (`docs/tauri-port/00-PLAN.md:95-105`). The visible result ranges from “old app still opens” to apparently missing preferences/library state.

Make the direct-download path safe in the **same Tauri NSIS preflight**:

1. Detect the legacy executable/uninstall entry and inspect `%APPDATA%\Nora` for `migration-ready`/`migration-complete` before writing anything.
2. If `migration-ready` exists, continue with the exact install-over flow above.
3. If legacy Electron exists but the marker does not, make no install changes. Offer to download and launch the fixed, signed final Electron bridge from its immutable tag, verifying a pinned hash, then exit. The bridge exports localStorage and re-invokes the Tauri installer. If offline or verification fails, leave the Electron installation untouched and present retry/manual instructions.
4. If no legacy install exists, use the clean-install path. If legacy data exists without the executable, preserve it and offer an explicit recovery/import path; never assume it is disposable.

This also means a standalone Tauri installer must not blindly kill/uninstall “Nora,” recreate shortcuts, or delete the legacy WebView data. The installer and bridge should use atomic markers with version/schema fields so crashes can resume idempotently.

### B5. Windows bundle choice

**Recommendation: Tauri NSIS, current-user scope, with a version-controlled custom installer template pinned to the tested Tauri v2 minor. Do not use MSI/WiX for the bridge.**

| Option | Fit with existing contract | Identity/install-over control | Update implications | Recommendation |
|---|---|---|---|---|
| Tauri NSIS `.exe` | Closest to today's per-user, non-elevated NSIS executable and silent update behaviour (`electron-builder.yml:64-87`, `build/installer.nsh:1-8`). | Tauri's template supports `/S`, `/UPDATE`, `/R`, custom pre/post-install hooks and shortcut AUMID stamping. Its stock directory is wrong, so a custom template must force `%LOCALAPPDATA%\Programs\Nora` before UI/copy and preserve an existing shortcut rather than delete/recreate it. | `tauri-plugin-updater` emits/signs NSIS update artifacts directly. No blockmaps; full download. | **Use this.** It minimizes changed variables while exposing enough control for the migration transaction. |
| MSI/WiX | Different installer technology and commonly machine-wide/Program Files oriented; it does not match the proven electron-builder NSIS lifecycle. | Product/upgrade GUIDs, scope and advertised shortcut rules introduce new identity axes. It can be customized, but proving it will retain a per-user NSIS install location and existing `.lnk`/pin is substantially harder. | Tauri can bundle/sign MSI, but switching installer family during the highest-risk update adds no user benefit. | Do not use for the bridge. Reconsider only as a later, separately migrated enterprise distribution channel. |

The relevant Tauri NSIS implementation currently restores prior install locations, exposes installer hooks, writes the uninstall entry and sets the shortcut AUMID to the bundle identifier ([installer template](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-bundler/src/bundle/windows/nsis/installer.nsi), [shortcut utility](https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-bundler/src/bundle/windows/nsis/utils.nsh)). Those are implementation details on the development branch, not a stable public guarantee. Vendor/pin the tested template and diff it deliberately when upgrading Tauri.

## Release-blocking validation matrix

No bridge release should become Published until all of these pass on Windows 10 and 11, x64 and ARM64 where available:

- Clean Electron 3.4.5 → feed-selected Electron bridge → silent Tauri handoff → first native boot.
- Direct current Tauri installer on a 3.4.5 machine with no marker → safe bridge detour, including offline and hash/signature-failure cases.
- Clean Tauri install; Tauri-to-Tauri signed update; rejected bad signature; architecture-correct selection.
- Realistic copied `%APPDATA%\Nora` profiles, including every JSON store and Chromium localStorage export/import; failed import and interrupted installer resume.
- Start Menu shortcut byte/path continuity where practical, unchanged target path and AUMID, existing taskbar pin launching/grouping correctly, and no duplicate Nora entries.
- Protocol auth, all audio file associations, Unicode/space-containing file paths, second-instance routing and launches before renderer readiness.
- Mixed-DPI monitor layouts and the rectangle clamp, including the known 50/50 straddle case.
- Tray, custom titlebar, mini/main geometry, always-on-top, battery/theme changes, sleep blocker, Discord pipe reconnect and Explorer restart/taskbar thumbbar recreation.
- Published-release audit: strict `vX.Y.Z-CMR-Fork`, full legacy asset set while supported, native installers/signatures, both manifests, direct URLs and signature verification.

The go/no-go criterion is not merely “Tauri launches.” It is that an unmodified 3.4.5 installation can follow the public feed, retain all user data, and launch from its already-pinned taskbar icon into the same Windows application identity.
